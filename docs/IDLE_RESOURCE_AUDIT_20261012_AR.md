## الأسباب المثبتة

1. **قراءة منحازة للمراقبة نفسها:** شغّل جامع القياسات وDjango importer معًا عبر pipeline. تحميل Django وفحوصه داخل حاوية الويب يحدث أثناء أخذ لقطة Docker، فأظهرت قياسات توثيق الدورية متوسطًا يقارب **45.7%** في الساعة السابقة بينما متوسط CPU الحقيقي للخادم كله **18.2%**. المقارنة هنا تكشف عدم قابلية اللقطة اللحظية للمقارنة بمتوسط الفترة.
2. **تحميل متكرر بلا طلبات:** الوكيل يبدأ Django للنبضة، ثم يبدأ خيطًا يرسل نبضة أخرى فورًا، ثم يبدأ Django مرة ثالثة لطلب عمل. يتكرر ذلك كل دقيقة حتى إذا كانت قائمة الأعمال فارغة، مع فحوص Django الكاملة لكل أمر.
3. **إخفاء فشل الجمع:** مسار `flock ... || exit 0` كان يعامل فشل الجامع/المستورد كتزاحم قفل عادي ويعيد نجاحًا.
4. **أحمال مستقلة عن توثيق:** قياس cgroup لمدة 62.3 ثانية سجّل CPU الخادم **17.74%**، وحاوية ويب توثيق **3.315%**. مجموع حاويات توثيق نحو **4.36%**. مشاريع أخرى تستهلك الباقي؛ هذه النسب من قدرة الخادم كاملة، وليست من نواة واحدة.

## الإصلاح

- دمج heartbeat وclaim في عملية `poll` واحدة مع الحفاظ على claim/heartbeat القديمة للتوافق.
- بدء نبضات العمل الطويل بعد 45 ثانية، وعدم إنشاء خيط أو عمليات إضافية عندما لا يوجد عمل. يبقى cron كل دقيقة، وتبقى حماية القفل وحدود الدفعة ومهل الأعمال.
- نقل الفحوص الشاملة إلى موضعها الموجود في CI والنشر، وعدم تكرارها في أمري العمليات الدوريين.
- إكمال جمع القياس قبل تحميل مستورد Django؛ الملف المؤقت محمي بصلاحيات mktemp ويحذف حتى عند الفشل.
- استخدام فرق عداد CPU التراكمي لكل حاوية بين تشغيلات الجامع، مع إبطال الحالة القديمة عند إعادة التشغيل/تبديل الحاوية/انقطاع الجمع. تبقى لقطة Docker بديلًا موسومًا صراحة عند أول قياس أو غياب cgroup v2.
- حفظ مصدر CPU ومدة العينة داخل بيانات كل حاوية.
- التمييز بين انشغال القفل وفشل الجمع/الاستيراد، وإعادة رمز الفشل الحقيقي.
- إضافة وضع GitHub Actions للقراءة فقط (`diagnostics`، `READ-ONLY`) قابل للتكرار دون إعادة تشغيل أو نسخ احتياطي أو تعديل بيانات.

يعتمد قياس CPU التراكمي على [عدادات Docker/cgroup](https://docs.docker.com/engine/containers/runmetrics/)؛ وضبط فحوص الأوامر يستخدم [واجهة Django الرسمية](https://docs.djangoproject.com/en/5.2/howto/custom-management-commands/#django.core.management.BaseCommand.requires_system_checks).

## التحقق

تغطي اختبارات الانحدار: poll الخامل، التقاط العمل مرة واحدة، انتهاء الدفعة دون حجز عمل غير منفّذ، نبضة الأعمال الطويلة، إعادة التشغيل وإعادة ضبط عدادات CPU، تطبيع CPU حسب عدد المعالجات، ترتيب الجمع والاستيراد، إزالة الملف المؤقت، وإظهار فشل الجمع الحقيقي.

تضاف نتائج CI والنشر والقياس اللاحق بعد اكتمالها. قياس دقيقة واحدة ليس ضمان أداء طويل الأجل ولا يمثل ساعات الذروة.
